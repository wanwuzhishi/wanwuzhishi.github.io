弹幕助手多源聚合：给一个没有源码的 App 接三个数据源

2026-11-07 软件工具 / 逆向工程 / Android / 弹幕 / 数据聚合

一个 Android 悬浮弹幕工具的数据源扩展实践：在没有可重编译源码的前提下，用 Java 扩展 dex + smali 桥接接入乐视、搜狐、AcFun 三个新源，并把「命中第一个源就停」改成「九源并行搜索 + 合并去重」。附实测数据、去重策略、标题匹配收紧的四条规则，以及踩过的坑。

弹幕助手是一个 Android 上的悬浮弹幕工具：你在别的 App 里看剧，它把弹幕浮在视频上面。它自己不产生弹幕，全部来自外部数据源——爱奇艺、腾讯、优酷、B站那些公开接口。

这个项目做的事，是给它接三个新来源（乐视、搜狐、AcFun），并把「命中第一个源就停」改成「九个源并行搜索 + 合并去重」。结果是一部剧的可用弹幕从千级到万级：甄嬛传从 8,000 条变成 24,089 条。

接口都不难。难的是这个 App 没有源码。

起点：一份不可重编译的产物

宿主应用是 Kotlin 1.9 + 协程编译出来的 APK，没有公开的 Gradle 工程。这意味着一件很容易被低估的事：你没法「下载源码、加个类、重新构建」。

反编译能拿到 smali，甚至能拿回看起来像 Java 的东西，但那不是能重新编译回等价产物的源码——协程被展开成状态机、lambda 被内联、R8 混淆后类名与方法名大面积丢失。硬还原的结果是一个编译不过、或者编译过了行为也变了的东西。

所以改造只能在「产物层」做，而不是「源码层」。

怎么做：Java 扩展 dex + smali 桥接

最终方案分两半：

新来源的逻辑全部写在纯 Java 类里。 HTTP 请求、JSON 解析、错误处理、重试，都在自己的类中完成，编译时只依赖 android.jar 和几个签名桩（stub）——桩只声明方法签名，保证编译期能过，运行时链接到原 App 里的真实实现。编译产物是一个独立的 dex，直接追加进 APK。

原应用里只注入 5 处桥接。 在 SourceManager 的相关位置插调用：源列表构建、来源名称映射、单源加载分派、检索分派、合并入口。

这样切分的理由是降低出错面：桥接只做路由判断，不碰原应用的状态机与协程逻辑。一旦去改那边的代码，就要面对整个 UI 状态流转是否还成立的问题，而这类退化没法靠单点测试发现。

把复杂度关在自己的 Java 代码里，还有两个附带好处：编译期能查出方法签名拼错、能单独写测试跑接口，不用每次装整包试。

原来的检索逻辑有两个坑

原逻辑是逐源顺序检索，谁先命中就用谁，后面的源直接不查。听起来省时间，实际有两个问题：

先命中的不一定是最好的。 搜「甄嬛传」，乐视给了 8,000 条就直接停了，而优酷其实有 16,081 条。用户拿到的弹幕密度只有应有的一半多一点。

新加的源排在列表末尾，几乎永远轮不到。 前面六个源只要有一个命中，新源根本不会被执行。也就是说，光「加源」不「改检索」，加了等于没加。

改成「主源快、其余并行」

新逻辑分两步：

  1. 九个源按顺序探测，第一个命中的作为主源——保证点击到出画面的响应速度；
  2. 主源确定后，其余八个源并行检索，各自 8 秒超时，返回什么算什么；
  3. 所有结果按 时间（0.1 秒精度） + 模式 + 文本 去重后合并，按时间轴升序排列；
  4. 界面上标出主源与参与合并的源，例如「乐视 + 腾讯视频 + B站 + 优酷」。

实测数据（同一台设备、同一网络）：

关键词 单源结果 合并结果 耗时 主源
甄嬛传2012电视剧 8,000 24,089 4.9s 乐视
法医秦明 5,626 25,988 4.6s 搜狐
葬送的芙莉莲 2,256 8,613 3.2s 爱奇艺
狂飙 17,700 17,700 2.1s 爱奇艺

识别结果与运行日志：主源乐视，参与合并的源直接写在来源行里

截图里的运行日志把这 24,089 条拆得很清楚：

乐视 8,000 + 优酷 16,081 + 腾讯视频 6 + B站 2 = 24,089。也就是说，对这部剧，优酷的存量是主源乐视的两倍，而腾讯视频和 B站各只贡献了个位数——九个源之间的覆盖率差异就是这个量级。

这张表里还有两条值得单独看的信息。

收益差异极大。 甄嬛传翻了 3 倍，法医秦明翻了 4.6 倍，葬送的芙莉莲 3.8 倍，而狂飙一条没涨——因为爱奇艺单源就已经吃满了，其余八个源没有多出来的存量。合并策略不是万能的，它的收益完全取决于各源的覆盖率。

代价是确定的。 单次检索慢 2–3 秒。对「点一下等片子出弹幕」这个场景，这个延迟可以接受，但它是净支出，不会因为结果好看而消失。

合并策略的几个细节

  • 线程池固定 8 线程，刚好对应「主源之外的八个源」，不会因为并发过高把设备打满；
  • 每源 8 秒超时，单源失败或超时不影响整体——少一个源，结果集小一点，但不会整个失败；
  • 去重键是 round(t * 10) + "|" + mode + "|" + text。时间戳先归一到 0.1 秒再比较，是因为不同来源的浮点精度不一致：同一句弹幕在一个源里是 12.345、在另一个源里是 12.35，不归一就永远去不掉重；
  • 排序按时间戳升序，这个不能省——合并后如果按来源拼接，弹幕会在画面上来回跳。

一个必须收紧的地方：标题匹配

新源接进来之后最先炸的不是接口，是标题匹配。

最初的匹配过于宽松：搜「狂飙」，命中了《少妇哭喊有人抢孩子……狂飙7分钟》这种标题里带关键词、但内容完全无关的视频，还把它的 1,000 条弹幕当主源拉了回来。用户看到的是莫名其妙的弹幕。

最后收紧成四条规则：

  1. 标题精确相等，直接通过；
  2. 候选以关键词开头时，长度不得超过关键词长度的 4 倍 + 4；
  3. 候选包含关键词时，长度不得超过关键词长度 + 2；
  4. 关键词包含候选时，关键词长度不得超过候选长度的 3 倍 + 6。

同时去掉了「时长接近就算匹配」这条兜底——它看起来能提高命中率，实际上是把一堆同名不同片的资源放进来了。

原则是：宁可不命中，也不给无关弹幕。命不中，用户换个片名再搜就是了；命错了，用户会以为这个功能坏了。

AcFun 那边还额外加了 danmuCount >= 20 的过滤：弹幕数是个位数的结果直接丢掉，那种基本是名字撞上了，不是用户要找的。

三个新源各自的门槛

  • 乐视：搜索结果页拿剧集，弹幕走 hd-my.le.com 的接口，按 300 秒分片拉取——分片粒度是接口本身定的，改不了。
  • 搜狐：搜索接口需要 md5 签名，弹幕接口要 vid + aid 两个参数配合才能取到。
  • AcFun：走 pc-direct 的公开接口，resourceType 固定传 9。

这三个都不是「标准公开 API」，是读协议、试参数、对签名试出来的。这也是为什么接一个源的工作量远大于写一个 fetch()。

鉴权是签名式，不涉及 OAuth：

Path 是不含查询参数的接口路径，比如 /api/v2/comment/12345。调用场景也很克制：用户播放动画时触发一次搜索，匹配成功后按集拉取一次弹幕，都是异步请求，没有后台轮询、没有批量爬取。

已知限制

  • 弹弹play 没有凭据时静默跳过，不报错也不占位；
  • B站需要登录 Cookie，未登录会触发 v_voucher 风控，这个源直接失效；
  • 乐视、搜狐的 UGC 覆盖本来就少，冷门片名可能一个结果都没有；
  • 合并会让单次检索慢 2–3 秒，换的是 2–4 倍的弹幕量；
  • 咪咕、芒果TV 没接——需要推导加密参数，成本太高；巴哈姆特、PPTV 接口当前不可达。

它不是什么

  • 不是一个新的 App。它是宿主应用的数据源扩展，没有宿主就没有意义。
  • 不分发安装包。仓库里只有实现说明、验证结果和截图，不提供 APK。
  • 不是爬虫。所有请求都发生在用户主动播放某个片名之后，一次性、无轮询、不落库。
  • 不碰账号数据。不读 Cookie 之外的东西，不存用户身份，不采集设备标识。
