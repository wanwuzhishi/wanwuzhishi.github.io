KSU Root：给 Redmi K90 Max 开一个重启就消失的临时 root

2026-10-26 软件工具 / 开源工具 / KernelSU / Shizuku / Android / 提权 / SukiSU 更新于 2026-11-21 15:55

把「电脑 + adb + 手工命令」的提权流程封装成一个 Android App，手机上点一下拿到 uid=0 的临时 root，重启即失效。v1.2.9 已从 CVE-2026-64560 迁到 CVE-2026-98260：不再需要 kprobe 布防，真机首次跑通零 panic。附双系统版本支持、SukiSU 与 KernelSU 双管理器、失败后为何必须先重启，以及已知限制。

这台 Redmi K90 Max（代号 prague）现在可以在手机上点两下拿到 root：不用电脑、不刷机、不解锁 Bootloader。当前版本 v1.2.9，支持澎湃 OS 4.0.0.14 和 4.0.5.0 两个系统版本。

代价还是那两条：重启就没了；它不是 Magisk，没有模块系统、没有隐藏、不会开机自启。

这不是一个给所有人用的 root 方案。它是一段已经被人研究透的漏洞利用链，被我封装成了一个能重复点击的 App。

2026-11-21 更新：仓库从发布这一篇时的 v1.0.3 迭代到了 v1.2.9，改动比版本号看起来大得多——v1.2.0 起整条链从 CVE-2026-64560 换成了 CVE-2026-98260，不再需要 kprobe 布防，真机首次跑通零 panic。另外，上一版这里写的「看 loadavg 决定要不要开」是错的，原因见下面那一节。

这一代换了什么

上一版用的是 CVE-2026-64560（posix-cpu-timers 的 UAF）。那条链的竞争窗口只有 14 条指令，大约 10 ns，必须靠 kprobe 在 posix_cpu_timer_del+72 人为制造延迟才抓得到——实测无扰动时 21 次全 miss。

v1.2.0 起换成 CVE-2026-98260：exec 在 de_thread() 之后、exec_mmap() 之前没有清理 POSIX CPU timer。窗口由父进程要不要 wait4() 决定，理论上是无限的。

CVE-2026-64560（v1.0.x ~ v1.1.x） CVE-2026-98260（v1.2.x）
竞争窗口 14 条指令，约 10 ns 由 wait4() 决定，理论上无限
kprobe 布防 必须，靠它在 posix_cpu_timer_del+72 拖时间 不需要
tracefs 需要 不需要
触发层 多线程抢那段精确时序 B 线程建 32 个 CLOCK_THREAD_CPUTIME_ID timer 后 execv，S 线程循环 mprotect 抢 mmap 写锁，逼 exec_mmap() 失败
真机首次运行 两次里一次 panic 一次跑通，零 panic、零重启

洞在哪，四步：

  1. 非 leader 线程 execve() 时，begin_new_exec() 先调 de_thread(me)，把 leader 的 struct pid 从 PIDTYPE_PID 哈希桶里摘掉（transfer_pid(leader, tsk, PIDTYPE_TGID) + release_task(leader)）。
  2. 接着调 exec_mmap(bprm->mm)。这一步失败返回，begin_new_exec() 走 goto out，跳过后面的 posix_cpu_timers_exit(me)。
  3. 在此之前，posix_cpu_timer_del() 会调 cpu_timer_task_rcu(timer)，也就是 pid_task(it.cpu.pid, PIDTYPE_PID)。桶已经空了，返回 NULL，函数直接 goto out——不 disarm，k_itimer 对象照常被释放。
  4. 定时器红黑树里就留下一个指向已释放对象的节点。等 cleanup_timerqueue() 对这颗节点做 timerqueue_del → rb_erase_cached，rb_next() 读到的 node->rb_right 正好落在 SLUB 对象的 freepointer 位置（s->offset = object_size/2），于是拿一个垃圾指针去解引用——panic。

触发条件比较挑：

  • clock 必须是 CLOCK_THREAD_CPUTIME_ID。进程级的 CLOCK_PROCESS_CPUTIME_ID 走 PIDTYPE_TGID，桶是完好的，没有 UAF。
  • 定时器得真的入树：SIGEV_SIGNAL、it_value 给一个很大的值、信号被 sigmask 挡住。
  • leader 必须活着。group_dead 一旦为真，整棵树会被清干净，反而没洞。
  • 必须让 exec_mmap() 失败。

上游的修复是把 posix_cpu_timers_exit() 提前到 de_thread() 紧后面执行，不等 exec_mmap()。

起点：一条只有电脑能走的链

ChaYeWuu 把 prague 上的完整利用链公开了——上一代在 prague-CVE-2026-64560-OS4.0，这一代在 prague-CVE-2026-98260-OS4.0。偏移、失败模式、每个 stage 在干什么，写得非常细。

但它是一套给电脑用的命令行流程：

每一步都能出错，每一步都要人盯着终端看输出判断下一步。做一次很爽，做第五次就开始想：为什么不能是个按钮？

封装之后，一条命令变成一个按钮

电脑上原本要做的 现在在手机上
插线、adb push 载荷 App 自动部署到 /data/local/tmp
adb shell -tt ./pk64560 --run 自写 ptyrun 分配伪终端后运行
手动往 root shell 里敲 ksud 命令 捕获 interactive root child 后自动注入
su -c id 验证 自动验证并把结果写进状态行

（载荷在仓库里的文件名还叫 pk64560，是历史遗留：现在放的是上游 98260 那版 payload/libexploit.so 的原样拷贝，2,296,288 B，静态链接 ET_EXEC，没有 PT_INTERP。）

成功的标志很明确：su -c id 返回

context=u:r:ksu:s0 是 KernelSU 的证据——普通 su 拿到的会是不一样的 SELinux 上下文。界面上则是状态行变 root: 已开启、模块: kernelsu 已加载，再弹一个「root 已就绪」。

它不是什么

这一段比上面那段重要。

  • 不是持久化 root。不碰 boot 分区，重启即失效。想要持久化就去走解锁 Bootloader + 刷 KernelSU 补丁的正路，别指望这个。
  • 只支持这一台机器、这一版内核。代码里有严格的机型和指纹校验，不匹配直接退出。这不是保守，是 hazard：内核地址、结构体偏移、slab 参数全是在这一版内核上量出来的，换一版可能不是”失败”，而是把内核写坏。
  • 不是 Magisk。没有模块系统、没有隐藏、没有开机自启。
  • 不保证一次成功。新链比旧链稳得多，但不是 100%——stage0 仍要精确的时序，drain 不干净时需要 ATTEMPT_DEFER 重试，最坏情况要等好几分钟。

支持的设备只有这一台，两个系统版本：

为什么 4.0.5.0 也能用

那个 OTA 没有重编内核。把 8.96 GB 的 full payload 里 boot 分区解出来，镜像和 4.0.0.14 是同一个二进制：版本串、git hash、ABO build id、编译时间（#1 SMP PREEMPT Mon Jul 20 18:34:35 UTC 2026）全部相同，CVE-2026-64560 的上游修复（920f893f）也不在其中。逐地址反汇编核验过 9 个关键偏移。

一个坑：OTA 的 META-INF/com/android/metadata 里 post-build 写的是预发布串 17OS4.0.261020.233332783.MTPECN.S，真机安装后 getprop ro.build.fingerprint 报的却是 OS4.0.5.0.XAACNXM。v1.0.4 只认前者，会在正式版机器上被 gate 拒绝；v1.0.5 起同时认两个串。

判断标准看 uname -r 和 ABO build id，不是看系统版本号。内核一变，全部硬编码偏移作废。

前置条件：三件东西

1. Shizuku 已经在跑。

从 RikkaApps/Shizuku 下官方版——不要用各种”优化版””内置 adb 版”，实测有假包。然后用无线调试或 adb 启动服务，并授权给这个 App。

2. 内核管理器装着，SukiSU Ultra 或 KernelSU，二选一。

  • SukiSU Ultra（优先）或 tiann/KernelSU
  • 不需要它现在是”工作”状态，只需要装在那儿——App 会在运行时从它的 APK 里抽出 ksud
  • 两个都装也行，默认按 SukiSU → KernelSU 取第一个能用的；想指定，点主界面的「管理器」那行切换
  • ⚠️ ksud 和内核模块必须来自同一个管理器：late-load 加载的就是 ksud 自带那份 ko。混用会 uapi 不匹配，管理器一直报”需要更新内核”
  • 换了管理器分支之后必须先重启再点按钮。旧模块还在内核里，新 ko 会因为模块名 kernelsu 重名而加载失败（File exists）
  • SukiSU 不同版本里 ksud 的伪装文件名会变（实测 libfdbqiupsrx.so → libtqqfthevwb.so，大小从 6,102,016 变成 6,093,280）。App 在 lib/arm64/ 下按大小自动找，不用手动指定

3. 如果之前手动跑过，把旧的 .ko 改名。

必须改名，否则 exploit 会加载那个 uapi=2 的旧模块，管理器会一直报”需要更新内核”。

用起来是什么样

首次：

  1. 启动 Shizuku，确认 App 状态行显示 Shizuku: 已就绪
  2. （可选）点 管理器 那行，确认要用哪个。默认「自动」；两个都装时建议手动选一次
  3. 点 开启 root
  4. 读一遍风险提示，点 我已知晓风险，继续
  5. 等 1–10 分钟，期间不要退出 App

主界面 · 风险确认 · 运行日志

[5/5] 会弹一个「等待 root 生效」的进度框——那是在等 ksud late-load 把 su 装好，不是卡住了。这一步有 240 秒硬上限。

之后想关掉 root，点 关闭 root（重启）。这是唯一可靠的方式——内核内存已经被改过，没法热恢复，只能靠重启清干净。

每次重启后都得手动启动 Shizuku

Shizuku 是用户态进程，不在 init 服务表里，重启就没了。两种启动方式：

手机上（推荐）：设置 → 开发者选项 → 无线调试打开 → 回到 Shizuku 点启动（首次点”配对”输六位码，配一次就够）→ 授权本 App。

电脑 adb：

官方启动器是伪装成 .so 的 native 可执行文件，必须带 --apk= 参数，直接 app_process 调会立刻退出。

MIUI 的坑：如果配对码通知不显示，去「设置 → 通知管理 → 通知显示设置」把通知样式改成「原生样式」。

开机自启不可靠：Shizuku 的 BootCompleteReceiver 虽然留了 ADB 分支，实测三次重启只有一次真的拉起来，adbStart() 大多数时候没执行。别指望它。

换 Shizuku 实现？先看权限名

App 走的是官方 dev.rikka.shizuku:api，能不能用取决于两件事，缺一不可：保留名为 "shizuku" 的 binder service 和 IShizukuService 的 AIDL 全名；保留 moe.shizuku.manager.permission.API_V23 这个权限名——官方 API 库把它硬编码在 checkSelfPermission() 里，fork 改成自己前缀后就永远请求不到授权。

失败是常态，但判据变细了

失败之后必须先重启，不能直接重试。 这条仍然成立，而且是最容易被忽略、代价最大的一条。

exploit 中途失败时（PIPE_PREP_FAIL、ATTEMPT_MISS 这类），它会自己打一行 KERNEL_STATE_RESTORE_PASS dirty=0，看起来把内核收拾干净了。其实没有：restore_misc_list 只把 misc_list 的头指针指回去，中间那个伪造的 miscdevice 节点没有从链表里摘下来，而它指向的内存已经被释放。

这时候手机一切正常——getenforce 还是 Enforcing，boot_id 还是原来那个，照样能用。但只要你再点一次「开启 root」，下一次 misc_open 遍历链表就会踩到那块已释放内存，直接 panic。pstore 里留下的是：

那个 x23 正是上一轮日志里打印过的 MISC_LIST_RESTORE_SCAN head。

v1.1.0 起 App 用三种结局区分这件事，不再”失败过就一律拒绝”：

结局 含义 要不要重启
GATE_REFUSED 入口就被拦下，没碰内核 不用
CLEAN_RESTORE 跑过，但确实收回去了 不用
TOUCHED 改过内核内存且没干净 必须重启

以前只看”上次是不是失败退出”，会把压根没执行 exploit 的情况也算进去，白让你重启。现在只有 TOUCHED 才拦。

另一个残留：悬空的 victim timer

ATTEMPT_DEFER 会把停在 pause() 的 victim 故意留着不 reap（这是设计的一部分，为了不打断后续轮次的时序）。这些 victim 每个挂着若干悬空 timer 节点，多轮 DEFER 之后会累积。长时间锁屏进深度休眠、系统集中回收 slab 时可能踩到，表现是「root 成功后锁屏十几分钟突然重启」。

v1.1.15 起加了 retire_victims_safe()：defer 之前先 kill victim、把 timer freelist 排空再决定要不要 waitpid。没排空就放弃这一轮、不 reap。

别再拿 loadavg 判断能不能开

上一版这一节写的是：App 会读 /proc/loadavg，load1 > 8 或开机不到 5 分钟就提示”偏高”，还附了四条”降低失败率”的做法，理由是系统忙的时候调度抖动会把 stage0 的窗口打偏。

那条建议是错的，得撤回。

这台机器的 /proc/loadavg 长期显示 19–21，但 top 是 757% idle、procs_running=1、/proc/pressure/cpu 全 0。读数被不可中断睡眠（D 状态）污染了，它根本不反映 CPU 忙不忙。按这个数字判断，等于永远显示”别开”。

v1.1.11 起 App 直接把这条提示删了。状态卡片还显示 loadavg，但只作参考，不要用它决定开不开。

真正还有效的只有：失败了先重启，别在重启后 90 秒内连点。

原理（简述）

对照上一代：[1] 从”线程抢 10 ns 窗口”变成了”用 mprotect 造 exec_mmap() 失败”，[2] 之后的受控写、spray、bridge 思路一脉相承，只是对象大小从 256B 变成 264B（31 槽位）。

两个细节值得单独说：

  • [7] 必须用 ptyrun 分配伪终端。exploit 拿到 root 后会 execve("/system/bin/sh", "-i")，而 sh -i 没有 tty 会立刻退出，注入的命令就被外层 uid=2000 的 shell 接走——表现是”明明注入了却没反应”。早期用 busybox script 分 pty，为了去掉那 1.4 MB 的 GPL-2.0 二进制，换成了自己写的 ptyrun（app/src/main/cpp/ptyrun.c）。
  • ksud late-load 不能拆开。exploit 的 payload 只做 finit_module，不创建 /data/adb/ksu/bin/su 和 /system/bin/su——这两个是 late-load 的用户空间安装部分做的。只加载模块不安装，结果就是「模块在、su 永远不出现」。v1.2.6 起让 payload 跳过模块加载，整个「加载 + 安装」都交给 ksu_load_setup.sh 的 late-load 一次做完。

已知限制

  • 重启即失效，没有持久化。
  • 每次重启要手动启动 Shizuku。
  • 会关掉 KernelSU 的 shell_su_adb_only：这条 feature 只放行 adbd / ksu 域派生的进程用 su，而本 App 走的是 Shizuku（ppid=1），不关就必然失败。关掉之后，任何以 shell 身份运行的进程都能用 su，安全性弱于默认值——这是本工具能工作的前提，用之前请知情。
  • 失败后必须先重启（尤其 TOUCHED）。
  • 可能残留悬空 timer 节点：多轮 ATTEMPT_DEFER 之后 victim 携带的节点会累积，锁屏深度休眠时可能崩溃。v1.1.15 的 retire_victims_safe() 会尽量排空。
  • 不能用 boot_id 判断是否重启：stage0 会改写它，跑完会变成 d8f06902-80ff-ffff-80e2-d6dcd6ffffff 这类假值。要用 /proc/uptime。
  • 只支持这一版内核（4.0.0.14 与 4.0.5.0 共用同一个内核二进制），换内核别试。
  • /proc/loadavg 在本机不可信：长期 19–21，实际 757% idle。别拿它当判据。

构建

改了 app/src/main/cpp/ptyrun.c 之后必须重编：

app/src/main/assets/pk64560 是上游 prague-CVE-2026-98260-OS4.0 的 payload/libexploit.so 原样拷贝（2,296,288 B）。要改它就得回上游改 C 源码重编，本仓库不含那份源码。

依赖版本：AGP 8.13.2 / Gradle 9.1.0 / Kotlin 2.0.21，compileSdk 36 / minSdk 26 / targetSdk 34。Shizuku 依赖锁在 dev.rikka.shizuku:api:12.2.0——13.x 的 Shizuku.newProcess() 是 private，外部调不了。gradle-wrapper.properties 里的 distributionUrl 指向腾讯云镜像，在海外可以换回官方。

安装：MIUI 会拦 adb install（INSTALL_FAILED_USER_RESTRICTED）。有 root 时用 su -c "pm install -r app-debug.apk"，否则在开发者选项里打开「USB 安装」。

仓库里还附了一份 AI-GUIDE.md，把流程拆成可执行命令、每个检查点的判据，以及明确的禁止操作边界。如果你的 AI 工具能读仓库内文档（Claude Code、Cursor、Codex 之类），直接把仓库喂给它就能照着跑。
