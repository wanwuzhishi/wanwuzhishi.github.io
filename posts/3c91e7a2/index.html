KSU Root：给 Redmi K90 Max 开一个重启就消失的临时 root

2026-10-26 软件工具 / 开源工具 / KernelSU / Shizuku / Android / 提权 更新于 2026-10-26 01:50

把「电脑 + adb + 五段手工命令」的提权流程封装成一个 Android App：Shizuku 转发、KernelSU LKM 加载、pty 注入，手机上点一下拿到 uid=0 的临时 root，重启即失效。附前置条件、40% panic 的成因、断点续跑、失败后为何必须先重启，以及已知限制。

这台 Redmi K90 Max（代号 prague，澎湃 OS 4.0.0.14）现在可以在手机上点两下拿到 root：不用电脑、不刷机、不解锁 Bootloader。当前版本 v1.0.3。

代价说清楚：重启就没了，而且大概四次里有三次能成，剩下一次会把内核干到 panic 重启。

这不是一个给所有人用的 root 方案。它是一段已经被人研究透的漏洞利用链，被我封装成了一个能重复点击的 App。

起点：一条只有电脑能走的提权链

ChaYeWuu 把 prague 上 CVE-2026-64560（posix-cpu-timers 的 UAF）的完整利用链公开了——偏移、失败模式、每个 stage 在干什么，写得非常细。但它是一套给电脑用的命令行流程：

每一步都能出错，每一步都要人盯着终端看输出判断下一步。做一次很爽，做第五次就开始想：为什么不能是个按钮？

封装之后，一条命令变成一个按钮

电脑上原本要做的 现在在手机上
插线、adb push 五个载荷 App 自动部署到 /data/local/tmp
adb shell sh kp_arm.sh 布防 kprobe 自动布防并校验返回值
adb shell -tt ./pk64560 --run 自写 ptyrun 分配伪终端后运行
手动往 root shell 里敲 ksud 命令 捕获 ROOT_CHILD_HOLD_PASS 后自动注入
su -c id 验证 自动验证并把结果写进状态行

成功的标志很明确：su -c id 返回

context=u:r:ksu:s0 是 KernelSU 的证据——普通 su 拿到的会是不一样的 SELinux 上下文。

它不是什么

这一段比上面那段重要。

  • 不是持久化 root。不碰 boot 分区，重启即失效。想要持久化就去走解锁 Bootloader + 刷 KernelSU 补丁的正路，别指望这个。
  • 只支持这一台机器、这一个系统版本。代码里有严格的机型和指纹校验，不匹配直接退出。这不是保守，是 hazard：内核地址、结构体偏移、slab 参数全是在这一版内核上量出来的，换一版可能不是”失败”，而是把内核写坏。
  • 不是 Magisk。没有模块系统、没有隐藏、没有开机自启。
  • 不保证成功。stage0 靠几个线程的精确竞争时序拿窗口，系统一忙就有概率翻车，翻车的表现是 panic 而不是报错。

支持的设备只有这一台：

前置条件：三件东西

1. Shizuku 已经在跑。

从 RikkaApps/Shizuku 下官方版——不要用各种”优化版””内置 adb 版”，实测有假包。然后用无线调试或 adb 启动服务，并授权给这个 App。

2. KernelSU 管理器装着。

不需要它现在是”工作”状态，只需要它装在机器上——App 会在运行时从它的 APK 里抽出 ksud。这么做是为了不分发 GPL-3.0 的二进制，同时保证 uapi 版本跟已装的管理器匹配。

3. 如果之前手动跑过，把旧的 .ko 改名。

必须改名，否则 exploit 会加载那个 uapi=2 的旧模块，管理器会一直报”需要更新内核”。

用起来是什么样

首次：

  1. 启动 Shizuku，确认 App 状态行显示 Shizuku: 已就绪
  2. 点 开启 root
  3. 读一遍风险提示，点 我已知晓风险，继续
  4. 等 3–8 分钟，期间不要退出 App

主界面 · 风险确认 · 运行日志

之后想关掉 root，点 关闭 root（重启）。这是唯一可靠的方式——stage0 改过内核的 random_table，没法热恢复，只能靠重启清干净。

每次重启后都得手动启动 Shizuku

Shizuku 是用户态进程，不在 init 服务表里，重启就没了。两种启动方式：

手机上（推荐）：设置 → 开发者选项 → 无线调试打开 → 回到 Shizuku 点启动（首次点”配对”输六位码，配一次就够）→ 授权本 App。

电脑 adb：

官方启动器是伪装成 .so 的 native 可执行文件，必须带 --apk= 参数，直接 app_process 调会立刻退出。

MIUI 的坑：如果配对码通知不显示，去「设置 → 通知管理 → 通知显示设置」把通知样式改成「原生样式」。

开机自启不可靠：Shizuku 的 BootCompleteReceiver 虽然留了 ADB 分支，实测三次重启只有一次真的拉起来，adbStart() 大多数时候没执行。别指望它。

换 Shizuku 实现？先看权限名

App 走的是官方 dev.rikka.shizuku:api，能不能用取决于两件事，缺一不可：保留名为 "shizuku" 的 binder service 和 IShizukuService 的 AIDL 全名；保留 moe.shizuku.manager.permission.API_V23 这个权限名——官方 API 库把它硬编码在 checkSelfPermission() 里，fork 改成自己前缀后就永远请求不到授权。

实现 包名 权限名 状态
RikkaApps/Shizuku moe.shizuku.privileged.api moe.shizuku.manager.permission.API_V23 ✅ 实机跑过
HmnDev-Tech/shevery com.hamondev.shevery 保留 moe.* ✅ 实机跑过
yangFenTuoZi/Shizuku 同上 同上 ⚪ 同包名同权限，理论可用
rushiranpise/Shizuku-Next 同上 同上 ⚪ 同上
thejaustin/ShizukuPlus（dropin） 同上 af.shizuku.plus.permission.API_V23 ⚪ 权限名不同，未测
thejaustin/ShizukuPlus（独立版） af.shizuku.plus.api af.shizuku.plus.permission.API_V23 ❌ 授权会失败
kerneldroid/Nightzuku kerneldroid.nightzuku kerneldroid.nightzuku.permission.API ❌ 授权会失败

打 ❌ 的两个，App 能识别出”装了”，但授权会失败，状态行显示 Shizuku: 版本不兼容。另外这些 fork 签名冲突，只能装一个。

失败是常态，不是 bug

大约 40% 的概率，stage0 会在 slab 竞争阶段触发内核 panic。手机黑屏自动重启，等 40–60 秒。

重开 App，主按钮会变成 继续上次（已中断）。App 把当前步骤写进 SharedPreferences，重启后通过 elapsedRealtime 变小判断出”被整机重启打断”，所以不需要你回忆跑到哪了。启动 Shizuku，点继续，接着跑。

连续两次 panic 就别硬刚了：正常重启一次让 SELinux 回到 Enforcing 再试。panic 之后那一轮 boot，MTK AEE 可能让 SELinux 停在 Permissive，这时候再跑会在 STAGE8_ENV_GATE 因为 enforcing=0 失败。

干净失败比 panic 更阴：不重启就再跑必崩

panic 至少是当场告诉你”这一轮废了”。更麻烦的是那种看起来没崩的失败。

exploit 中途失败时（PIPE_PREP_FAIL、ATTEMPT_MISS 这类），它会自己打一行 KERNEL_STATE_RESTORE_PASS dirty=0，看起来把内核收拾干净了。其实没有：restore_misc_list 只把 misc_list 的头指针指回去，中间那个伪造的 miscdevice 节点没有从链表里摘下来，而它指向的内存已经被释放。

这时候手机一切正常——getenforce 还是 Enforcing，boot_id 还是原来那个，照样能用。但只要你再点一次「开启 root」，下一次 misc_open 遍历链表就会踩到那块已释放内存，直接 panic。pstore 里留下的是：

那个 x23 正是上一轮日志里打印过的 MISC_LIST_RESTORE_SCAN head。

所以 v1.0.3 起，App 在开跑之前会检查上次是不是失败退出且还没重启过，是的话直接拒绝并提示你重启，不再让你白跑一趟——白跑的结果就是 panic。这一版之前没有这道闸，只能靠人记住。

成功率跟系统负载强相关

stage0 拿的是几个线程之间的精确竞争窗口。系统忙的时候调度抖动大，窗口被打偏，rb_erase 就会拿一棵对不上的红黑树去改内存——失败的表现就是 panic，栈长这样：

这台机器（OS4.0.0.14）负载常态偏高：刚开机 load average 能到 20–35（8 核，也就是 2.5–4 倍超载），此时失败率明显比上游说的 40% 高。

所以 App 会读 /proc/loadavg 和 /proc/uptime，直接显示在状态卡片第 5 行：

显示 含义
系统: 负载 3.2 适合开
系统: 负载 34.1 · 偏高，建议等系统闲下来再开 现在点大概率 panic

判断标准是 load1 > 8 或开机不到 5 分钟。只是提示，不拦你点。

v1.0.3 顺手把「刚开机」和「负载偏高」拆成了两种文案——更早的版本两条规则会同时命中，显示成「负载 0.0 · 偏高」这种自相矛盾的提示。

降低失败率的实际做法：

  1. 别急着重试。panic → 重启 → 系统重新拉起一堆后台服务 → 负载又上去了，90 秒内再点等于重蹈覆辙。
  2. 关机放一会儿再开，或者重启后等 5–10 分钟。
  3. 关掉常驻后台应用（微信、淘宝这类），它们对 load 的贡献不小。
  4. 注意 load 是1 分钟平均值，关掉应用不会立刻见效。

原理（简述）

有一个细节值得单独说：[6] 必须用 ptyrun 分配伪终端。exploit 拿到 root 后会 execl("/system/bin/sh", "sh", "-i")，而 sh -i 没有 tty 会立刻退出，注入的命令就被外层 uid=2000 的 shell 接走——表现是”明明注入了却没反应”。

早期版本是用 busybox script 来分 pty 的，为了去掉那 1.4 MB 的 GPL-2.0 二进制，现在换成了自己写的 ptyrun（app/src/main/cpp/ptyrun.c）。在真机上 tty 返回 /dev/pts/0，能正常往 sh -i 里注入命令。

实测记录

这台机器上两次完整跑通：

时间 场景 结果
2026-10-25 22:02 冷启动，一次过，约 5 分钟 su -c id → uid=0 / u:r:ksu:s0
2026-10-25 23:08 到 [4/5] 时 panic 重启 → 断点续跑 同上；uptime=162 证明重启过

这两次是在 1.0.0 的早期构建上跑的，那一版用 busybox script 分 pty、ksud 随 APK 分发。之后陆续换成自写 ptyrun、运行期从已装管理器抽取 ksud，v1.0.3 又加了「上次失败且没重启过就拒绝开跑」这道闸。这些改动的关键路径都单独验证过——ptyrun 在真机上 tty 返回 /dev/pts/0、能往 sh -i 注入命令；ksud 提取返回 5172384 字节且对 shell 可读——但这几版合起来的完整流程尚未在真机上复测。跑通了或者跑挂了，都值得开个 issue。

已知限制

  • 重启即失效，没有持久化。
  • 每次重启要手动启动 Shizuku。
  • 开过 root 之后内核里有颗延迟炸弹：posix_cpu_timer_del 相关的 dangling timer 节点会留在内核里，之后任意进程调 timer_delete 都可能 panic 重启（pstore 里能看到 posix_cpu_timer_del+0x140 的 Oops）。重启一次清除。
  • 不能用 boot_id 判断是否重启：stage0 会改写它，跑完会变成 d8f06902-80ff-ffff-80e2-d6dcd6ffffff 这类假值。要用 /proc/uptime。
  • 只支持一个系统版本，换版本别试。

构建

改了 app/src/main/cpp/ptyrun.c 之后必须重编：

依赖版本：AGP 8.13.2 / Gradle 9.1.0 / Kotlin 2.0.21，compileSdk 36 / minSdk 26 / targetSdk 34。Shizuku 依赖锁在 dev.rikka.shizuku:api:12.2.0——13.x 的 Shizuku.newProcess() 是 private，外部调不了。

安装：MIUI 会拦 adb install（INSTALL_FAILED_USER_RESTRICTED）。有 root 时用 su -c "pm install -r app-debug.apk"，否则在开发者选项里打开「USB 安装」。

仓库里还附了一份 AI-GUIDE.md，把流程拆成可执行命令、每个检查点的判据，以及明确的禁止操作边界。如果你的 AI 工具能读仓库内文档（Claude Code、Cursor、Codex 之类），直接把仓库喂给它就能照着跑。
